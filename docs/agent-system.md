# 多 Agent：以玩家价值划分职责

日期：2026-11-07。状态：产品与接口设计，尚未实现模型编排或接通模型服务。

## 1. 为什么需要多个 Agent

Agent指能围绕一个目标选择知识、调用受控工具并产出结果的智能助手。这里的多Agent不是让多个角色同时聊天，而是让不同职责各自解决一种学习障碍。角色名称、模型数量与玩家价值分别考虑：一个模型可以承担多个隔离角色，某个角色也可以由自部署模型、外部API或确定规则完成。

玩家只需要提出“给我一点线索”“换个玩法练练”“这是真的吗”“接下来去哪里”。界面默认只由一个向导回应。后台按需要调用对应职责，避免多份重复解释、长时间等待与额外费用。

首要价值顺序：更少搜索、更容易够到下一步、更能独立解决问题、知识关系更清楚、结果可信且可回看。角色数量不能作为质量指标。

## 2. 每个角色解决什么问题

| 玩家眼前的问题与入口 | 角色及职责 | 给玩家的具体结果 | 与其他角色的边界 | 验证价值的方法 |
| --- | --- | --- | --- | --- |
| “卡住了，给一点线索” | 引路人 tutor：分层提示、换例子、术语桥接 | 一次一个线索；必要时只补当前缺少的先修 | 不泄露独立评价答案，不直接判掌握 | 下一步能独立行动；与整段答案相比提示量更小；记录提示依赖 |
| “再来一个，我想试试” | 陪练师 practice：从已审阅模板选变式、诊断误解 | 数值/情境不同但目标相同的可玩练习与即时规则反馈 | 出题不能给自己签发掌握证书；同题族变式不算独立证据 | 无效题比例、条件可满足性、覆盖与重复率，独立新题表现 |
| “为什么是这样？资料在哪里？” | 资料向导 research：基于图谱检索并定位证据 | 简明回答、来源位置、适用条件、已知争议 | 不能把搜索摘要当已核查事实；未知就报告缺口 | 引用可打开、命题获来源支持、搜索成功率与玩家找资料耗时 |
| “我真的懂了吗？能跳过吗？” | 验证官 assessment：独立迁移、解释与关系核验 | 通过/局部缺口/待复核，以及对应证据与复验安排 | 独立于陪练上下文；不可只数关键词；模型结论仅作评价候选 | 与人工量规一致性、误通过/误拒绝、等价解释公平性、纠正记录 |
| “这些知识怎么连起来？” | 绘图师 cartographer：把玩家原话整理成关系提案 | 1—3条有条件的连线、出处与可选修订预览 | 不自动改公共事实或覆盖个人图；玩家采纳后新建修订 | 玩家能解释新关系；正确连线/误连线，采纳后可恢复 |
| “接下来学什么，太难/太简单怎么办？” | 领航员 navigator：诊断、路线、补桥、复验 | 当前少量可达探索点，简短推荐原因，可主动换路 | 解锁资格由证据规则决定；模型只建议，不凭聊天次数跳级 | 过难/过易轮次、必要基础遗漏、误跳、无意义重复、推荐可解释性 |
| “这里过时或有错” | 知识维护员 curator：后台收集、变更与影响分析 | 修复通知、版本变化、受影响内容与是否需复验 | 不主动打断游玩；新事实/生成关卡须审校后发布 | 可追溯纠错时长、来源覆盖、关键错误漏检、旧成果可回看 |

验证官与领航员不能相互替代：前者判断现有证据支持什么，后者决定在这些证据下安排什么学习行动。资料向导和引路人也不能合并为无边界聊天：前者负责“有何依据”，后者负责“本轮怎样够到”。

## 3. 从游戏里如何出现

回声小岛失败时，先用本地规则给一条光路线索；玩家仍困惑才请求引路人。通关后“换个场景”由陪练师提供可验证变式；“这与Transformer有什么关系”由资料向导查当前图谱邻域和来源；“我懂了，直接去后面”交给独立验证官，验证结果再由规则领航员决定是否开放新节点。

绘图师在玩家有表达和实验证据后才提出连线，先让玩家看“将新增什么”，采纳后存新版本。维护员在后台工作，其产物通过版本发布到游戏，不把未经审核的生成文档直接放入玩家路线。

玩家不会看到七个对话窗口。请求结果先压缩成一条可行动反馈，来源、完整推导和过程在玩家主动展开时显示。随时可关闭助手，保留固定关卡和资料。

## 4. 统一接口与服务边界

以下均为目标契约，不是当前已有接口。

| 接口 | 用途 |
| --- | --- |
| GET /api/v1/agent-capabilities | 返回当前可用角色、动作、是否离线、配置预算下的运行限制；不返回密钥 |
| POST /api/v1/agent-runs | 提交一个玩家意图，服务端路由与执行；立即返回run_id与状态 |
| GET /api/v1/agent-runs/{run_id} | 轮询状态与结构化结果，可选SSE进度；不返回隐藏推理过程 |
| POST /api/v1/agent-runs/{run_id}/cancel | 尽力取消；标记取消，不将迟到结果应用到状态 |
| POST /api/v1/graph-proposals/{id}/accept | 按base_revision检查后将已预览的个人图修订写为新版本 |
| POST /api/v1/evaluations/{id}/review | 追加复核或纠正，不覆盖原评价 |

一次请求的主要字段：

```json
{
  "intent": "hint",
  "operation_key": "uuid",
  "context": {
    "content_release": "release-id",
    "entity_ids": ["entity-0068"],
    "relation_ids": [],
    "quest_id": "island-mask",
    "quest_version": "island-mask-v1",
    "graph_revision": 4,
    "attempt_id": "attempt-id"
  },
  "input": {"message": "我关了光闸，为什么前面的数没变？", "hint_level": 1}
}
```

学习者身份从服务端会话取得，不信任请求体中的owner。当前本地演示档案不得直接当作正式多用户身份实现。客户端传入ID、版本与允许的玩家输入，不上传整个私有图谱或评分答案。

结果至少包含：run_id、status、role、action、player_message、evidence_refs、proposal_id（若有）、uncertainties、review_status、content/quest/rubric/prompt/provider/model版本、timing、可获得的usage与费用信息。无法获得费用时明确unknown，不编造为0。

状态明确区分queued、running、completed、needs_review、failed、cancelled。客户端重试以operation_key返回同一次运行；同键不同内容拒绝，图修订、证据入库和奖励各有幂等约束。异步作业在持久化队列中执行，不能靠进程内临时任务保证恢复。

## 5. 多角色如何协作

编排器先读取版本与权限，再按意图走最短路径。例如“这是真的吗”通常只走检索，不必调用陪练、绘图和验证。只有依赖明确时才串联，多份独立证据可并行检索。结果冲突时呈现具体不确定项或进入人工复核，不能用多数模型投票当事实证明。

每轮先给一个响应；初版运行上限建议为最多2个角色、3次模型调用、15秒等待。这些是待实测的工程预算，不是已保证的服务指标。复杂维护任务异步执行并显示状态；超预算及时退回固定提示、已有资料或可继续的规则关卡，不无限重试。

## 6. 知识、出题和评价的数据隔离

- **检索域**：公共已发布知识、来源与当前图谱邻域、玩家明确允许的个人记录分开索引。版本过滤后检索，引用必须能定位，无法命中时报告缺口；外部网页文本视为资料，不作为系统指令。
- **练习域**：陪练读取练习模板、适用先修、参数范围与练习规则。生成结果先过Schema、数值求解、可达性、答案一致性和误解检查；不能生成任意代码让主服务执行。新公共关卡进入草稿/审校，不能直接发布。
- **评价域**：独立挑战与量规仅由验证流程访问，不进入辅导检索。记录是否看过提示、题族与生成来源；同题变式不能叠加成独立验证。
- **写入权限**：模型输出仅是候选。规则检查后才能提交作答/证据；图提案由玩家采纳；公共事实由维护发布流程审核。每类结果绑定当时版本，保留纠错和撤回影响记录。

## 7. 自部署与外部API可替换

定义统一Provider适配层，暴露generate_structured、stream、工具调用能力、健康状态和实际usage。角色配置指定provider、model、提示版本、允许工具、超时、预算与回退，不把厂商字段写进关卡规则。

先做无模型确定规则适配器，用固定提示与检索验证流程。随后接一个自部署或外部API适配器，再通过同一套样本验证等价行为。供应商、模型和部署地址待实际接入时核查，不在计划里虚构已可用服务。

切换提供方不能静默扩大数据外发：本地模式默认资料和个人数据留本地，改为外部服务时说明将发送的最小上下文与提供方。密钥只在服务端，调用额度由配置执行，日志不保存凭据。调用失败保留作答和图草稿，不授予未知掌握状态。

## 8. 分步开发与验收

1. **A0：价值与样本**：为七种意图各收集至少5个玩家问题，标明有用结果、过度回答和错误行为。先做场景集，再决定是否需要独立角色。
2. **A1：最小闭环**：capabilities、agent-runs、幂等与版本记录；实现本地图谱检索与分层规则提示。客户端始终可在无模型状态完成固定关卡。
3. **A2：检索＋引路人**：接一个真实提供方，使用最小上下文；逐命题检查引用与超纲词。与固定内容比较，不以回答长短评价。
4. **A3：陪练＋验证官**：模板生成先经确定计算验证；独立评价隔离，上线前校准误通过与误拒绝。保留待复核与纠正路径。
5. **A4：领航员＋绘图师**：将诊断证据、先修与个人图快照接入；动态推荐少量探索点，个人修订需预览与采纳。先演示跳级/补桥与冲突恢复。
6. **A5：维护员与第二提供方**：来源变化进入影响队列；验证新旧版本回看和显式迁移；比较不同提供方在相同样本上的引用、误判、延迟和成本。

每步通过功能与学习样本检查后再扩展。至少覆盖检索无结果、来源冲突、伪引用、提示泄漏、生成无解、等价解释、模型不同意、接口超时、取消后迟到、重复请求、过期图修订、模型切换、费用未知与外部数据最小化。

## 9. 价值衡量的边界

先记录本地规则/固定资料的基线，再比较Agent是否减少必要搜索、减少过度提示、改善独立新题表现与关系解释，同时不增加关键误判或明显等待。用户自报“更喜欢”与实际学习证据分开。尚无真实试学，任何数值目标都应视为待校准假设。

若某个角色没有独立价值，合并其实现；若会让首屏更复杂，就把它留在后台。多Agent的结果应是玩家少操心，而不是玩家管理一队助手。
